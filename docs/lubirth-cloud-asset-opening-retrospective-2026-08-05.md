# LuBirth 云层资产开场复盘（REJECT）

- **日期：** 2026-08-05
- **范围：** `/lubirth-cloud-asset-opening` query-only 路由
- **封存提交：** `eee8aff feat(lubirth): surface-lock opening cloud assets`
- **结论：** **REJECT。** 分支保留为技术证据，不接入默认首页；本文完成时不推送、不创建 PR。

## 1. 要解决的产品问题

这一轮的目标不是做一段“地球视频”，而是让云层作为资产服务于真实的 IP 地球与运镜：

- 滚动 `0–0.18` 时，用户应明显看到云体自身连续演化，而不只是地球缩放或镜头变化；
- 云层必须贴合球面，并在近景里有可读的厚度、遮挡和层次；
- 开场到 Relief-lite 的接管不能出现全图切换、双影或明显的表示切层；
- 桌面与移动端均要在既定传输、首帧与内存预算内工作。

产品视觉验收没有通过。测试和构建通过只能证明状态机、资源管理和合同实现正确，不能替代“云是否真的成立”的判断。

## 2. 本轮实际交付了什么

最终实现没有把完整 Earth / 星空 / UI 烘焙成视频。它使用了一个 globe-UV 标量云场视频，并把它附着在真实 `earthGroup` 内：

- 普通 Relief-lite 云层从开场到接管始终挂载，作为不变的低层基础；
- 开场视频驱动一层紧贴球面的云体壳与一层高空薄 wisps；
- 离线场从同一 Relief-lite 云图采样 `128×64` 的低频地理锚点，并叠加有限的程序化变化；
- `TransitionVeil` 在 `0.18–0.22` 的遮挡窗口中执行原子切换；
- 帧寻址、反向重入、降级和资源释放均已实现并有自动化验证。

这套机制是“技术上可运行的云层资产管线”，但不是达成目标的摄影级云层表现。

## 4. 为什么仍然失败

### 4.1 云的变化不构成叙事

实际滚动时，感知最强的是地球尺寸和镜头关系；云场虽有帧变化，但变化主要是受限的局部程序化扰动，不能形成“云系在演进”的明显视觉事件。用户看到的是近似静态纹理随球体移动，而不是连续的天气结构变化。

**经验：** 只有“帧可寻址”不等于“视觉上有连续变化”。下一次必须以真实 IP 相机下 `0`、`0.06`、`0.12`、`0.18` 的并列画面先验收云的形态变化，再讨论运行时承载。

### 4.2 球面附着的数值正确，不等于视觉贴合

本轮统一了 Relief-lite 与开场云层的 UV / scroll offset，并把壳层压缩到 `1.0035–1.0074` 地球半径。它消除了明显的地理错位，但多层薄壳仍会在近景读成悬浮的棉团或一层贴图；数值半径接近也不会自动产生云底贴地、云顶起伏和地平线遮挡。

**经验：** “贴合球面”至少要同时通过三件事：地理位置一致、近景视差成立、云芯对背景和地表有可信的遮挡。仅校验 UV 和半径不够。

### 4.3 体积感的来源不足

目前的资产本质是 2D 打包场加少量薄壳采样。`128×64` 地理锚点保证大范围对齐，却也限制了可艺术指导的宏观云团；有限步数和单一视角下的高度/凹凸字段不足以塑造近景摄影级的体积、边缘透光、内阴影和层间视差。用户感到宇宙背景“透出来”，就是密度、遮挡与深度关系没有被建立的视觉症状，而不应只靠提高 opacity 掩盖。

**经验：** 若目标是近景摄影级云体，低成本 2D 场 + 薄壳不是足够的表示。继续给当前 shader、Hybrid 或 deep impostor 叠参数只会固化该上限。

### 4.4 遮挡式切换修复了机制，未修复视觉本体

全不透明 `TransitionVeil` 能可靠地隐藏 `0.195` 的原子切换，这是正确的工程边界；但它不能把两种视觉质量不同的云表示变成同一种云。只要 veil 打开后云的照明、密度或结构显著变化，用户仍会感知“一个云层和图片/另一层云的切换”。

**经验：** veil 只能作为最后的切换保障，不能成为视觉连续性的主要证据。交接两侧应先在无遮挡状态下达到可接受的形态、亮度与色彩一致性。

### 4.5 性能门禁没有被解除

先前封存的 Hybrid 路径在桌面测得 Relief-lite GPU p95 为 `4.233916 ms`，超过 `≤3 ms` 门槛；deep impostor 同样被拒绝。本轮 query-only 云层资产没有做物理真机 GPU p95 声明，因此不能把自动化通过当作性能放行。

**经验：** “浏览器可播放视频”不能绕开整体体验的帧时间和解码抖动。下一轮若保持摄影级体积感，应先重新谈定真实设备上的 GPU / CPU / 解码预算。

## 5. 过程上的失误

1. **机制先行，视觉资产后验。** 先建设 FrameProvider、路由、过渡和测试，直到真实页面才发现云本身不成立。以后必须先验收离线 master / 辅助资产，再写运行时代码。
2. **一度偏离“云是资产”的定义。** 全场景 plate 虽可提供第一眼摄影感，但会把真实 IP 地球替换成画面，不是本任务要的云层资产。这个方向应明确排除。
3. **把工程连续性误当作视觉连续性。** 持续基础层、相同 UV、零帧闪黑与反向可寻址都很重要，但它们不是摄影级云层的充分条件。
4. **缺少早期主观门禁。** 没有在第一个可看版本就用实际浏览器滚动进行“云变化是否明显、是否贴球、是否有厚度”的人工判定，导致在不成立的表示上投入过多。

## 6. 不应继续做的事

- 不再围绕当前 Hybrid、deep impostor 或这套 2D 打包场继续调 shader 参数；它们已不足以支撑目标。
- 不把完整 Earth / 星空 / 文字画面作为“云层资产”塞入默认首页。
- 不因为单测、构建和校验和通过就提升为默认首页方案。
- 不在新的高质量 source asset 通过视觉门禁前，继续扩展 FrameProvider、路由或转场机制。

## 7. 下一轮的前置门禁

下一步不是直接再写实现计划，而是先拿到能在真实 IP 相机内审看的云层 master / 辅助资产。它必须是云专用数据，而非全屏场景片：至少能提供覆盖、厚度/高度、照明或阴影等可在球面内合成的信息。

在任何运行时代码开始前，先针对 desktop 和 mobile 各给出 `0`、`0.06`、`0.12`、`0.18` 四个实际构图样本，并由视觉验收确认：

- 云系变化在滚动中可被直接感知，不依赖地球缩放来制造变化；
- 云底、云芯、云顶与球面 / 地平线关系成立，近景没有悬浮贴片感；
- 厚云区域不会不合理地透出宇宙或地表；
- 交接前后在无遮挡状态下亮度、色彩和云系结构已接近，veil 仅承担原子切换；
- 移动端安全裁切、压缩质量、传输、首帧和内存预算同时成立；
- 若要坚持摄影级体积感，则必须带着真实设备性能数据重新确认可接受的预算，而不是默认沿用 `≤3 ms`。

只有上述资产门禁通过，才值得重新选择承载方式和写新的实现计划。
